# MP-01 - Omnichannel Mock Data Foundation

## Intent

Create a large, coherent, reproducible dataset that behaves like data exported from
real marketing platforms and generated by users interacting with ads, websites,
email, and commerce systems. The dataset is both demo input and experimental ground
truth for correctness and performance evaluation.

Random independent CSV rows are explicitly out of scope. A purchase must be
traceable through a plausible journey and all aggregate ad reports must reconcile
with the simulated impressions, clicks, cost, and conversions that produced them.

## Goals

- Simulate multiple source systems with source-specific formats and field names.
- Preserve referential integrity across customers, campaigns, ads, sessions, events,
  products, orders, and email messages.
- Produce deterministic data from a seed without loading the full event set in RAM.
- Support laptop smoke tests, a substantial demonstration dataset, and benchmark
  scales that can grow beyond memory.
- Include controlled data-quality conditions needed to prove deduplication, late-data
  handling, validation, consent, and reconciliation.
- Make generated events directly usable by a later Kafka replay tool.

## Non-goals for MP-01

- Connecting to real advertising APIs.
- Publishing to Kafka; MP-02 owns transport and replay pacing.
- Building Iceberg, ClickHouse, PostgreSQL, Flink, Dagster, dbt, API, or UI services.
- Generating or copying real personal information.
- Perfectly reproducing every field from every vendor API version.

## Data domains

| Dataset | System represented | Format | Grain | Key relationships |
|---|---|---|---|---|
| `master/customers` | CRM customer master | CSV gzip | one row/customer | `customer_id` |
| `master/products` | Product catalog | CSV gzip | one row/product | `product_id` |
| `master/campaigns` | Cross-platform campaign registry | CSV gzip | one row/campaign | platform campaign ID |
| `master/ads` | Platform creative/ad registry | CSV gzip | one row/ad | campaign and ad IDs |
| `google_ads` | Google Ads daily report | CSV gzip | campaign/day | derived metrics |
| `meta_ads` | Meta Ads Insights-like report | JSONL gzip | campaign/day | derived metrics |
| `tiktok_ads` | TikTok Ads daily report | CSV gzip | campaign/day | derived metrics |
| `web_events` | Web/mobile analytics SDK | JSONL gzip | one row/event | click, session, customer, product |
| `orders` | Commerce/transaction service | JSONL gzip | one row/order lifecycle event | session, customer, order |
| `crm` | CRM daily snapshot/change feed | CSV gzip | customer snapshot/change | customer and consent |
| `email_events` | Lifecycle messaging provider | JSONL gzip | one row/message event | customer and campaign |
| `ground_truth` | Evaluation-only reference | JSONL gzip | campaign/day/channel | expected KPIs |

Ad platforms normally expose aggregated reports rather than user-level impression
logs. Therefore impressions and advertising cost appear in vendor report files,
while clicks are connected to first-party web events using `gclid`, `fbclid`, or
`ttclid`. This boundary intentionally mirrors real integrations.

## Journey model

For each simulated ad impression:

1. Select a platform, active campaign, ad, market, device, and event time.
2. Accumulate platform-specific impressions and cost.
3. A click may occur based on campaign quality, platform, hour, device, and seeded
   random variation; it receives a platform click ID.
4. A click creates a landing-page session containing `page_view` and optional
   `view_item`, `add_to_cart`, `begin_checkout`, and `purchase` events.
5. Identified sessions reference a synthetic CRM customer; anonymous sessions retain
   an anonymous ID and can identify later in the journey.
6. A purchase emits both a web `purchase` event and commerce `order_created` event.
   Some orders later emit `order_refunded`.
7. Vendor daily conversions and conversion value are derived from these purchases.
8. CRM and email feeds reuse the same customer identifiers and respect consent.

The model intentionally includes daily and hourly seasonality, campaign quality
differences, platform mix, device mix, product price variation, and funnel drop-off.

## Stable identifiers and privacy

- IDs use deterministic UUIDv5 values derived from namespace, seed, entity type,
  and ordinal, so repeated runs are byte-for-byte stable.
- Synthetic email addresses use the reserved `.test` domain.
- Phone-like values are synthetic tokens, not dialable numbers.
- Data is labeled `synthetic: true` in manifests and event metadata.
- Raw records include `consent_analytics` and `consent_marketing` where relevant.

## Time, currency, and attribution rules

- All timestamps are RFC 3339 UTC values ending in `Z`; partition dates are derived
  from `event_time` in UTC and never from the machine timezone.
- Every profile defaults to `2026-01-01T00:00:00Z`. The CLI may override the UTC
  start date with `--start-date YYYY-MM-DD`; the chosen value is part of the manifest
  and therefore part of reproducibility.
- The only version-1 currency is `VND`. Business amounts use integer `*_minor`
  fields where one minor unit equals one VND. Google-compatible `cost_micros` uses
  one-million micros per VND; generated costs are exact multiples of one million.
- Vendor conversions use last paid click within seven 24-hour periods before the
  purchase, evaluated by UTC event time. The most recent eligible `gclid`, `fbclid`,
  or `ttclid` wins. Email touches do not change vendor conversion totals; they are
  retained for later multi-touch models.
- A user who identifies during a session attaches the earlier anonymous session to
  that customer in ground truth. The original raw events remain unchanged.
- A refund does not erase the original conversion. Vendor conversion value and
  `gross_revenue_minor` remain gross; `net_revenue_minor` subtracts refunds.

## Version-1 schemas

All CSV columns appear in the order listed. JSON objects use the same logical order
when serialized. `null` means the field is present with a JSON null value; blank CSV
cells represent nullable values. Integers are base-10 and booleans are `true/false`.

### Master files

- `customers`: `customer_id:str`, `email:str`, `phone_token:str`,
  `created_at:timestamp`, `country:str`, `city:str`,
  `loyalty_tier:enum[bronze,silver,gold]`, `consent_analytics:bool`,
  `consent_marketing:bool`.
- `products`: `product_id:str`, `sku:str`, `name:str`,
  `category:enum[electronics,home,beauty,fashion,sports]`, `brand:str`,
  `unit_price_minor:int`, `currency:enum[VND]`.
- `campaigns`: `campaign_id:str`, `platform:enum[google,meta,tiktok]`,
  `platform_campaign_id:str`, `name:str`,
  `objective:enum[awareness,traffic,conversions]`,
  `status:enum[active,paused]`, `start_date:date`, `end_date:date`,
  `daily_budget_minor:int`, `currency:enum[VND]`.
- `ads`: `ad_id:str`, `campaign_id:str`, `platform_ad_id:str`,
  `name:str`, `creative_format:enum[image,video,carousel]`,
  `landing_page_url:str`.

### Vendor reports

- Google Ads CSV: `segments_date:date`, `campaign_id:str` (vendor ID),
  `impressions:int`, `clicks:int`, `cost_micros:int`, `conversions:int`,
  `conversions_value:int` (VND).
- Meta Ads JSONL: `date_start:date`, `date_stop:date`, `campaign_id:str`
  (vendor ID), `impressions:str`, `clicks:str`, `spend:str` (whole VND), and
  `actions:list[{action_type:enum[purchase],value:str}]`,
  `action_values:list[{action_type:enum[purchase],value:str}]`.
- TikTok Ads CSV: `stat_time_day:date`, `campaign_id:str` (vendor ID),
  `impressions:int`, `clicks:int`, `spend:str` (whole VND), `conversion:int`,
  `total_purchase_value:str` (whole VND).

The campaign master is the controlled crosswalk from vendor IDs to canonical
`campaign_id`; vendor reports do not contain canonical IDs.

### Replayable event envelope

`web_events`, `orders`, and `email_events` are valid replayable sources. Every row
contains `event_id:str`, `event_name:str`, `event_time:timestamp`,
`ingested_at:timestamp`, `source:enum[web,mobile,commerce,email]`,
`schema_version:int=1`, nullable `customer_id`, `anonymous_id`, `session_id`,
`campaign_id`, `platform_campaign_id`, and `click_id`,
`consent_analytics:bool`, `is_late:bool`, plus `payload:object`.

- Web/mobile event names are `page_view`, `view_item`, `add_to_cart`,
  `begin_checkout`, and `purchase`. Payload uses nullable `product_id`,
  `page_url`, `device_type:enum[desktop,mobile,tablet]`, `market:str`, and for
  all web events `is_bot:bool`; purchase also includes `order_id`,
  `amount_minor:int`, `currency:enum[VND]`.
- Commerce event names are `order_created` and `order_refunded`. Payload contains
  `order_id`, `items:list[{product_id,quantity,unit_price_minor}]`,
  `gross_amount_minor`, `refund_amount_minor`, `currency:enum[VND]`, and nullable
  `attributed_platform` and `attributed_campaign_id`.
- Email event names are `email_sent`, `email_delivered`, `email_opened`,
  `email_clicked`, and `email_unsubscribed`. Payload contains `message_id`,
  `lifecycle_campaign_id`, and nullable `destination_url`.

Advertising reports, master files, CRM snapshots, and ground truth are batch-only
in MP-01. `quality_cases` is replayed by MP-02 specifically to test validation and
DLQ behavior; it is not treated as valid business data.

### Batch and evaluation files

- CRM CSV: `snapshot_date:date`, `customer_id:str`, `email:str`,
  `loyalty_tier:enum[bronze,silver,gold]`, `lifetime_value_minor:int`,
  `last_order_at:timestamp|null`, `consent_analytics:bool`,
  `consent_marketing:bool`.
- Ground truth JSONL: `date:date`, `campaign_id:str`,
  `platform:enum[google,meta,tiktok]`, `impressions:int`, `clicks:int`,
  `spend_minor:int`, `sessions:int`, `orders:int`, `gross_revenue_minor:int`,
  `refunds_minor:int`, and `net_revenue_minor:int`.
- Quality cases JSONL uses a valid wrapper:
  `case_id:str`, `event_time:timestamp`, `original_dataset:str`,
  `expected_error_code:enum[MISSING_REQUIRED_FIELD,UNSUPPORTED_SCHEMA_VERSION,ORPHAN_CLICK_ID]`,
  and `record:object`. The nested `record` is deliberately invalid. This permits
  deterministic JSON parsing before schema validation and supplies the expected DLQ
  reason for later tests.

## Required event fields

Every replayable event must contain:

| Field | Meaning |
|---|---|
| `event_id` | deterministic idempotency key |
| `event_name` | versioned business event name |
| `event_time` | when the simulated action occurred, UTC ISO-8601 |
| `ingested_at` | simulated source arrival time, UTC ISO-8601 |
| `source` | source system name |
| `schema_version` | integer contract version, initially `1` |
| `customer_id` | nullable synthetic customer identifier |
| `anonymous_id` | nullable browser/device identifier |
| `session_id` | nullable first-party session identifier |
| `campaign_id` | nullable canonical campaign identifier |
| `platform_campaign_id` | nullable vendor campaign identifier |
| `click_id` | nullable platform click identifier |
| `consent_analytics` | whether analytics processing is permitted |
| `payload` | source-specific attributes |

## Scale profiles

| Profile | Days | Customers | Campaigns | Impressions/day | Purpose |
|---|---:|---:|---:|---:|---|
| `fixture` | 2 | 100 | 6 | 500 | committed deterministic tests and examples |
| `smoke` | 3 | 2,000 | 12 | 10,000 | local functional check |
| `demo` | 14 | 50,000 | 30 | 150,000 | approximately 2.1M impressions for the presentation |
| `benchmark` | 30 | 250,000 | 60 | 1,000,000 | approximately 30M impressions for performance runs |

`demo` and `benchmark` outputs are local artifacts under `data/generated/` and must
never be committed. File writers rotate at configurable row counts so a profile
produces many date-partitioned source files rather than one giant file.

The committed fixture lives at `data/mock/fixtures/seed-360/`, is explicitly outside
the ignored generated-data directories, and must remain at or below 5 MiB compressed
in total.

## Controlled anomalies

The default profiles inject and count:

- Duplicate events with the same `event_id`.
- Late arrivals where `ingested_at` is hours after `event_time`.
- Invalid records with missing required fields or an unsupported schema version.
- Events without marketing consent.
- Bot-like sessions with implausibly high page-view rates.
- Refunds after purchase.
- Orphan click IDs in a dedicated invalid fixture.

Default rates are deterministic schedules over eligible records, not random draws:

| Anomaly | Rate / rule |
|---|---:|
| duplicate replayable event | 0.5% |
| late replayable event | 1.0% |
| invalid quality case | 0.2%, split across the three error codes |
| analytics consent denied | 5.0% of customers |
| bot-like session | 0.2% of sessions |
| refund | 5.0% of created orders |
| orphan click quality case | included in the invalid 0.2% allocation |

Each enabled anomaly has at least one occurrence in `fixture`. Larger profiles use a
deterministic ordinal schedule with interval `round(1 / rate)`, so realized rates
converge to the configured targets without retaining all events in memory. The
manifest records actual counts. Duplicate rows retain the same `event_id`; late rows
retain `event_time` and change only `ingested_at`.

Invalid records are written to an explicit `quality_cases` source so parsers can
consume valid JSON while downstream validation decides whether to accept or reject
each record. This makes every failure deterministic and explainable.
Every quality case starts from a complete valid event and introduces exactly one
defect, so all three expected DLQ reason codes can be demonstrated independently.

Email unsubscribe events change effective consent on subsequent UTC days. Later
email sends exclude those customers and CRM snapshots expose the updated marketing
consent state. A configured anomaly rate of zero disables that anomaly completely;
fixture coverage never overrides an explicit zero.

## Output contract

```text
data/generated/<run-id>/
├── manifest.json
├── master/
│   ├── customers.csv.gz
│   ├── products.csv.gz
│   ├── campaigns.csv.gz
│   └── ads.csv.gz
├── google_ads/date=YYYY-MM-DD/part-00000.csv.gz
├── meta_ads/date=YYYY-MM-DD/part-00000.jsonl.gz
├── tiktok_ads/date=YYYY-MM-DD/part-00000.csv.gz
├── web_events/date=YYYY-MM-DD/part-NNNNN.jsonl.gz
├── orders/date=YYYY-MM-DD/part-NNNNN.jsonl.gz
├── crm/date=YYYY-MM-DD/part-NNNNN.csv.gz
├── email_events/date=YYYY-MM-DD/part-NNNNN.jsonl.gz
├── quality_cases/date=YYYY-MM-DD/part-NNNNN.jsonl.gz
└── ground_truth/date=YYYY-MM-DD/campaign_metrics.jsonl.gz
```

`manifest.json` contains generator version, creation configuration, seed, profile,
UTC time range, schema versions, row counts by dataset, anomaly counts, file size,
SHA-256 per file, and expected aggregate totals.

## Command-line interface

```bash
python -m marketpulse_mock generate \
  --profile demo \
  --seed 360 \
  --output data/generated/demo-seed-360

python -m marketpulse_mock validate \
  --input data/generated/demo-seed-360

python -m marketpulse_mock profiles
```

The command fails before writing if the output directory already contains a
manifest, unless `--overwrite` is explicitly supplied. Overwrite may delete only
the exact validated output directory passed to the command.

## Acceptance criteria

1. Two fixture runs with seed `360` have equal relative paths, SHA-256 values, row
   counts, and aggregate truth values.
2. Changing the seed changes at least one master record and event checksum.
3. All valid foreign keys resolve and all purchase amounts reconcile between web,
   orders, platform reports, and ground truth.
4. Every replayable record has the required envelope and nondecreasing event time
   within its output partition.
5. Injected duplicate, late, invalid, no-consent, bot, and refund counts match the
   manifest.
6. Writers rotate at the configured limit and do not retain all events in memory.
   Overlapping journeys are merged through a bounded event-time priority queue;
   the generator never sorts or retains a whole day of events.
7. Validation detects a modified file, missing reference, broken funnel, and
   aggregate mismatch with actionable error messages.
8. The committed fixture remains small enough for Git; demo/benchmark paths are
   ignored.
9. The architecture and backlog identify MP-01 as implemented after tests and the
   demo generation complete.

## Builder decisions

The builder may choose compression level, internal module boundaries, and progress
logging format provided deterministic bytes, bounded memory, and the public CLI
contract remain unchanged.
